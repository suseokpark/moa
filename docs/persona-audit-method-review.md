# 합성 페르소나 사용성 점검: 독립 방법론 검토

- 검토일: 2026-09-24
- 기준: FAVMOA 0.1.28 소스와 기존 자동 테스트
- 목적: 관심사별 합성 페르소나 100개 × 시나리오 3개 = 300개 실행의 증거 품질 점검
- 범위: 아래 내용은 소스 검토와 합성 환경 재현이다. 실제 사용자 조사나 실제 Chrome 사용자 데이터 점검이 아니다.
- 제품 코드는 이 검토에서 수정하지 않았다. 브라우저 화면 검증은 별도 보고서와 연결해야 한다.

이 문서는 독립 사전 검토 시점의 기록이다. 이후 대표 화면 재현과 최종 300회 결과는 [최종 점검 기록](PERSONA-AUDIT-2026-09-24.md)에 정리했다. 아래의 `화면 확인 필요` 표시는 사전 검토의 증거 범위이며 최종 상태를 대신하지 않는다.

## 먼저 구분할 것

| 구분 | 주장할 수 있는 것 | 주장할 수 없는 것 |
| --- | --- | --- |
| 합성 페르소나 | 설정한 관심사·목표·입력 조건을 포함했다 | 실제 사용자 100명의 요구를 조사했다 |
| 자동 시나리오 실행 | 지정한 입력과 기대 결과에서 검사가 통과/실패했다 | 사용자가 쉽게 이해했거나 만족했다 |
| 전문가 휴리스틱 검토 | 실제 동작을 근거로 혼란 가능성을 지적했다 | 사용자 불편 발생률, 전환율, 성공률을 추정했다 |
| 브라우저 대표 흐름 확인 | 지정한 화면·뷰포트·행동을 직접 확인했다 | 300회가 모두 실브라우저 실행이었다 |

300은 사전에 정한 **실행 수**이지 표본 크기나 통계적 신뢰도를 뜻하지 않는다. 실행 결과의 통과 수·실패 수·미검증 수·고유한 동작 조건 수는 보고할 수 있지만, 이를 SUS·만족도·실제 사용자 성공률·시장 비중으로 바꾸어 표현하면 안 된다. 처리 시간도 실제로 측정한 기계 실행 시간에만 한정하며 사람이 느끼는 속도나 작업 시간으로 해석하지 않는다.

## 고가치 마찰 가설 5개

### H1. 단일 링크를 저장하거나 이동한 뒤 결과가 보이지 않을 수 있다

- 관심사/상황: 자료를 한두 개씩 정리하는 학습자, 요리·여행 자료 수집가. 이미 접힌 관심사 그룹에 새 자료를 넣고 저장 완료를 확인한다.
- 근거: `sidepanel.js:269–276`의 단일 추가는 `addLink`만 실행한다. 외부 검색 초기화나 목적지 표시가 없다. 모델 `link-library.js:375–381`은 링크를 추가하지만 접힘 상태를 유지한다. 단일 이동도 `sidepanel.js:279–283`, `link-library.js:412–417`에서 같은 특성을 보인다.
- 대조: 여러 링크 추가는 `sidepanel.js:740–750`에서 `revealTarget: true`, 검색 초기화, 목적지 포커스를 제공한다.
- 사전 재현: 실제 reducer에 접힌 그룹으로 단일 링크를 추가하면 링크 1개가 저장되고 그룹은 `collapsed: true`로 남는다. 모델 동작을 확인한 것이며 화면을 직접 본 증거는 별도이다.
- 기존 테스트의 빈틈: `sidepanel-dialog-usability.test.mjs`는 입력 오류·저장 대기·재시도를 검증한다. 단일 저장 후 외부 검색·접힘·스크롤을 결합한 결과 발견성은 검증하지 않는다. 배치 추가의 결과 표시 테스트만으로 이 흐름을 대체할 수 없다.
- 후속 검증: 검색어가 새 링크와 일치하지 않는 상태에서 접힌 하위 그룹에 저장한 뒤 결과 위치를 바로 알 수 있는지 확인한다.

### H2. 그룹을 접었다 펴는 행동이 직전 변경의 되돌리기를 대체한다

- 관심사/상황: 자료가 많은 연구자·개발자. 링크를 추가하거나 제거한 뒤 다른 그룹을 접어 화면을 정리하고, 직전 데이터 변경을 취소하려 한다.
- 근거: `sidepanel.js:403–407`은 폴딩을 저장 동작으로 보낸다. `favmoa-service.js:110–112`는 변화가 있는 저장마다 한 슬롯의 undo를 새 카탈로그 직전 상태로 덮는다. `sidepanel.html:44`에는 마지막 변경 1회라는 안내가 있지만, 폴딩이 그 한 번을 소비한다는 설명은 없다.
- 사전 재현: 실제 서비스와 합성 메모리 저장소에서 `링크 추가 → 그룹 폴딩 → 되돌리기` 실행. 폴딩만 취소되고 추가 링크는 남으며 `canUndo: false`가 된다.
- 기존 테스트의 빈틈: `open-tabs-add-service.test.mjs:79–91`은 배치 추가 직후 바로 undo를 검증한다. 사이에 시각적 정리 행동이 끼는 시퀀스는 별도다.
- 후속 검증: 제거와 폴딩을 연속 실행한 뒤 사용자가 어떤 변경을 취소할 것으로 예상할지 관찰한다. 데이터 변경과 화면 상태의 undo 정책 분리는 제품 결정이 필요하며 임의로 덮어쓰기해서는 안 된다.

### H3. 보관함을 바꾸어도 이전 검색어가 남아 새 보관함이 비어 보일 수 있다

- 관심사/상황: 업무·학습·취미를 별도 보관함으로 나눈 사용자. 업무 용어 검색 후 취미 보관함으로 전환한다.
- 근거: `sidepanel.js:838`의 기존 보관함 전환은 `libraryId`와 폴딩 override만 바꾸고 검색어를 유지한다. 반면 새 보관함 생성 후에는 `sidepanel.js:199–204`에서 검색어를 지운다.
- 사전 재현: 현재 코드가 실행되는 합성 DOM에서 검색어 입력 후 기존 보관함을 바꾸어도 검색어가 그대로 남는 것을 확인했다.
- 기존 테스트의 빈틈: `sidepanel-library-selection.test.mjs:47–58`의 생성 직후 검색 초기화는 기존 보관함 전환을 다루지 않는다.
- 반례/주의: 여러 보관함에서 같은 검색을 계속하고 싶은 숙련자에게는 검색 유지가 유용할 수 있다. 따라서 동작 자체를 확정 버그로 표기하지 말고, 유지 여부의 명시성·비어 있음과 검색 결과 없음의 구분을 확인해야 한다.
- 후속 검증: 기존 검색어를 보여주면서 결과 0개와 지우기 행동이 충분히 눈에 띄는지 대표 화면으로 확인한다.

### H4. 충돌 안내에 따라 다시 저장해도 같은 대화상자는 계속 충돌할 수 있다

- 관심사/상황: 여러 창으로 조사하는 대학원생·디자이너. 열린 탭 30개를 고른 동안 다른 FAVMOA 화면에서 목록이 바뀐다.
- 근거: `sidepanel.js:691`에서 캡처한 `revision`을 `740`의 제출 때 계속 사용한다. `requireResult`(`97–105`)는 충돌 시 최신 카탈로그를 반영하지만 대화상자의 캡처 revision은 갱신하지 않는다. 서비스 오류(`favmoa-service.js:78`)는 최신 목록 확인 뒤 다시 시도하도록 안내한다.
- 사전 재현: 기존 candidate-picker 합성 DOM fixture에서 충돌 후 두 번 제출. 화면 상태 revision은 8이지만 두 요청 모두 expectedRevision 7이었다. 선택은 유지되나 같은 창 재시도는 계속 충돌한다.
- 기존 테스트의 빈틈: `sidepanel-open-tabs.test.mjs:163–171`은 첫 충돌 후 선택 보존과 부분 저장 방지를 검증한다. 사용자가 안내에 따라 두 번째 제출하는 행동은 검증하지 않는다.
- 후속 검증: 안전한 명시적 재검토/재선택 경로를 보여준다. 자동으로 revision만 바꾸어 저장하면 중복·삭제된 목적지 등 새 상태를 검토하지 않은 덮어쓰기 위험이 있으므로 금지한다.

### H5. 가져오기를 시작한 뒤 새 관심사 그룹을 만들려면 선택을 포기해야 한다

- 관심사/상황: 새로운 취미·프로젝트를 시작한 사용자. 열린 탭이나 북마크를 먼저 고르고 저장할 그룹이 없음을 나중에 발견한다.
- 근거: `sidepanel.js:181–186`의 목적지는 기존 그룹 목록만 제공한다. 공통 가져오기 대화상자는 `799`에서 이 목록을 사용한다. 그룹 만들기 진입은 외부 도구 모음(`827`)이나 그룹 메뉴(`522`)에 있으며 선택 상태는 대화상자 지역 변수(`694`)이다.
- 증거 수준: 소스 기반 기능 간극이다. 아직 실제 화면에서 작업 중단이나 선택 유실을 확인하지 않은 가설이며, 모든 사용자에게 필요한 기능이라는 뜻도 아니다.
- 기존 테스트의 빈틈: 후보 선택·기존 목적지·저장 실패 보존 테스트는 새 목적지의 생성과 이어 저장하는 시나리오를 포함하지 않는다.
- 후속 검증: 가져오기 전 그룹 생성이 필요한지 알 수 있는지, 또는 선택을 보존한 채 목적지 그룹을 명시적으로 만들 수 있어야 하는지 대표 흐름으로 검토한다.

## 100 × 3 설계의 품질 기준

1. **관심사는 목표를 바꾸어야 한다.** 이름만 다른 100명에게 동일 URL·같은 목표를 배정하면 100개의 유효한 사용 맥락을 검토한 것이 아니다. 분야별로 자료의 제목·출처·폴더 깊이·중복 특성이 달라야 한다.
2. **관심사와 행동 조건을 분리한다.** 예: 여행 관심사가 저숙련·고령·모바일을 자동으로 뜻하지 않는다. 숙련도, 키보드 사용, 좁은 화면, 다중 창, 링크 규모, 보관함 수를 별도 축으로 교차 배치한다.
3. **페르소나는 가상임을 표시한다.** 허구의 이름보다 `P001`과 구체적 목적이 검토 추적에 유용하다. 개인·건강·인종·성별 정보나 가짜 인터뷰 인용은 필요 없다.
4. **3회는 독립 시나리오 ID를 갖는다.** 각 기록에 페르소나 ID, 관심사, 초기 상태, 과제, 조작, 기대 결과, 실제 결과, 증거 종류, 실패 이유를 남긴다. 실행 ID가 다르다는 이유만으로 고유한 조건이라고 계산하지 않는다.
5. **동작 범주를 공개한다.** 300개의 결과와 함께 실제로 달라지는 케이스/분기 수를 별도로 보여준다. 동일 reducer를 100개 제목으로 돌리는 검사는 강한 데이터 다양성 점검일 수 있으나 100개의 인터랙션 경로는 아니다.
6. **페르소나가 제품을 칭찬하게 만들지 않는다.** 결과는 기대 조건과 실제 관찰을 비교한 판정이어야 한다. 성격을 설정한 모델의 감상문을 실제 만족도나 연구 결과처럼 집계하지 않는다.
7. **해당 없는 조건을 통과 처리하지 않는다.** 브라우저 권한창, 스크린리더, 실제 드래그 좌표, 실제 Chrome 탭 재사용, 네트워크 지연은 mock만으로 확인할 수 없다. 명시적으로 미검증 또는 별도 확인 대상으로 둔다.
8. **실패의 단위를 섞지 않는다.** 같은 결함이 25개 페르소나에서 재현돼도 고유 결함 25개가 아니다. 고유 결함 수와 영향받은 합성 실행 수를 분리한다.
9. **단계 전체를 주장하지 않는다.** 소스 검사, 합성 DOM, 실제 모델·서비스, 브라우저 화면 관찰은 각 결과에 증거 종류로 표시한다. 자동 테스트가 통과해도 발견성·문구 이해·인지 부담이 해결됐다는 뜻은 아니다.
10. **개선 전후에 같은 케이스를 쓴다.** 실패를 통과로 만들기 위해 기대 결과나 입력을 수정한 경우는 별도 기록한다. 실행 당시 버전/커밋, 검증 명령, 결과 파일을 남긴다.

## 대표 브라우저 확인 권장안

1. 단일 링크를 접힌 목적지에 추가 → 저장 결과 위치를 찾기. 상태: 모델 마찰 재현, 화면 확인 필요.
2. 링크 추가/제거 → 그룹 접기 → 되돌리기. 상태: 서비스 시퀀스 재현, 사용자의 기대는 실사용자 확인 필요.
3. 좁은 검색 → 기존 보관함 전환 → 전체 목록 보기. 상태: 합성 DOM 동작 확인, 화면 명시성 확인 필요.

대량 후보 선택·충돌 재시도는 자동화가 유리하고, 실제 선택 발견성·키보드 포커스·좁은 화면 배치는 브라우저 확인이 유리하다. 브라우저 대표 3개를 300개 전체의 시각 검증으로 확대 해석하지 않는다.

## 다음 판정

현재 소스에서 일부 기능의 안정성이 충분히 테스트되어 있어도 **행동 사이에 끼는 탐색·폴딩·보관함 전환**과 **정상 저장 후의 결과 발견성**은 추가 검증 가치가 높다. 본 점검에서는 실행 수를 늘리는 것보다 이 교차 조건이 300개 목록에 실제로 포함됐는지 확인하는 것을 우선한다.
