# FAVMOA 0.1.36 · 기존 Moa 가져오기 충돌 복구

검증일: 2026-09-25 KST. [개선 큐](USABILITY-IMPROVEMENT-QUEUE.md) 2번에서 남아 있던 기존 Moa 가져오기 확인창을 완료했다. 지정된 대화상자의 충돌 복구 완료이며 모든 종류의 충돌 또는 실제 Chrome 화면 검증을 뜻하지 않는다. 다음은 3번 수동 추가·이동 결과 표시다.

## 재현과 원인

실제 sidepanel 진입점과 catalog service를 합성 DOM·메모리 저장소로 실행했다. revision 7 확인창에서 저장소 revision 8 변경 후 제출하면 화면 state는 8이지만 실행 버튼은 활성 상태였다. 확인창의 고정 revision closure와 명시적 재검토 경로 부재가 원인이다. 서비스는 stale 요청을 차단하며 이 단계에서 원본 조회/저장은 발생하지 않았다.

독립 소스 검토로 경고만 있고 가져온 보관함이 0개일 때도 ‘새 Moa 목록이 없습니다’라고 표시하는 경로를 찾았다. 손상된 합성 workspace로 이를 별도 RED 재현 후 수정했다. diagnose·TDD 절차로 기능별 재현→최소 수정→실제 서비스 회귀를 진행했다.

## 구현 계약

- `legacyImportDialog`가 마지막 `confirmDialog` 호출을 대체한다. 충돌 후 실행을 잠그고 **최신 대상 목록 검토**를 제공한다. 검토는 `platform.load()`/GET만 호출하고 원본 legacy 조회나 저장·Undo를 만들지 않는다.
- 최신 전체 catalog의 보관함/링크/이전 기록 수와 보관함별 그룹·링크 수를 확인한다. 가져오기는 기존 보관함의 교체가 아니라 새 보관함 추가이며 특정 활성 보관함으로 원본을 몰래 재지정하지 않는다.
- 검토 뒤 확인 체크와 별도 실행을 요구한다. 다시 검토하거나 충돌하면 체크를 해제한다. 버튼의 disabled 상태뿐 아니라 실제 submit에서도 게이트를 검사한다. 최초 명시적 가져오기와 일반 저장 실패 후 별도 재시도는 유지한다.
- 원본 목록은 가져오기 실행 시 읽는다. 이 화면은 대상 catalog 검토이지 원본 내용·추가될 개수의 미리보기 또는 고정된 원본 스냅샷이 아니라고 안내한다. 검토 후 바뀐 원본은 실제 실행 시 읽는다는 계약을 별도 시험했다.
- 현재 catalog에 이전 기록이 남은 workspace는 중복 복사·자동 동기화하지 않는다. 다른 창에서 먼저 가져온 경우 재검토에 최신 이전 기록을 보여주며 재실행은 no-op이다. Undo/JSON 복원이 이전 이력을 바꿀 수 있어 영구적인 중복 방지라고 표현하지 않는다.
- 원본 보존, 기존 보관함 보존, 첫 이전의 bounded legacy 사본, 원자적 저장, 일반 Undo 및 JSON 복원 전 사본 유지 계약을 변경하지 않았다. 서비스·모델·스키마·권한·저장 키·확장 ID는 그대로다.
- 0개 가져오기 + 경고는 빈 원본이 아니라 ‘확인 필요’로 표시한다. 일부 성공의 실제 개수/경고도 구분하고, 내부 원본별 경고 문자열을 그대로 노출하지 않는다.
- 실패·오래된/손상된 응답, 취소/다른 확인창 뒤 늦은 응답은 실행을 허용하지 않는다. 중복 읽기·쓰기, 확인 해제, 재충돌, 실제 storage.set 실패 후 데이터 불변과 명시적 재시도를 확인했다.
