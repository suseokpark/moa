# FAVMOA 0.1.23 QA — 드래그 이동과 클릭 응답

검증일: 2026-09-23 KST. 기준 버전 0.1.22 → 0.1.23, 다음 패치 0.1.24.

## 감사 범위와 목표

Chrome 사이드 패널에서 링크·그룹을 분류하고 링크를 여는 세 가지 흐름을 점검했다. 기본 조작이 눈에 보여야 하며, 드래그를 쓰지 않아도 키보드 이동 메뉴를 이용할 수 있어야 한다. `diagnose`의 재현·회귀 테스트 순서와 `product-design:audit`의 수정 전 화면 캡처를 사용했다. 기존 디자인 토큰·그룹 색·현재 페이지 표시를 유지했다.

실제 저장 데이터 대신 localhost 미리보기의 예시 링크와 이번 검증에서 만든 그룹 A/B만 조작했다. 노션 내부 화면·Google 연결·실제 계정 정보는 검증 대상이 아니다.

## 관찰 → 개선 → 확인

| 단계 | 수정 전 확인 | 0.1.23 개선 및 확인 |
| --- | --- | --- |
| 1. 그룹 추가 | `+ 그룹`이 회색 텍스트 버튼이라 링크 추가보다 발견하기 어려움 | 테마 강조색 글자·테두리와 연한 배경의 보조 버튼. 380px 라이트와 340px 라벤더 다크에서 확인, 340px 가로 넘침 없음 |
| 2. 분류 이동 | 메뉴 → 다른 그룹으로 이동 → 대상 선택 → 이동의 다단계 흐름. 드래그 이벤트 없음 | 링크를 그룹 A로 드래그, 그룹 A를 B 안으로 드래그, A를 최상위로 꺼내기 모두 실제 브라우저 입력으로 성공. 루트 드롭 영역은 고정 배치하여 드래그 시작 시 목록이 밀리지 않음 |
| 3. 이동 복구·키보드 | 기존 이동 메뉴와 되돌리기는 유용한 대안 | 최상위 이동 되돌리기, 검색 후 경로 유지, 키보드 Enter로 이동 메뉴/확정, 재시작 후 저장 유지 확인. 원래 예시 링크를 미분류로 돌려놓고 임시 A/B만 제거 |
| 4. 링크 열기 | 모의 Chrome API에서 조회 2회 순차 대기. 일반 연속 클릭 시 중복 탭 생성 | 독립 조회 병렬화, 같은 URL의 처리 중 일반 클릭 합류, 같은 창의 불필요한 포커스 요청 생략. UI에 즉시 `여는 중` 표시. 데모 링크 클릭으로 정확한 예시 주소의 새 탭 생성 확인 |

장점은 현재 링크와 저장 경로, 되돌리기, 명시적 이동 메뉴가 이미 분리되어 있었다는 점이다. 이 흐름을 대체하지 않고 드래그를 추가했다. 색뿐 아니라 커서·외곽선·설명 문구로 이동 상태를 전달한다.

## 재현과 회귀 테스트

- UI 회귀 6개 실패를 먼저 확인한 뒤 수정했다. 이후 명시적 새 탭 요청이 일반 클릭 대기 중 차단되지 않는 테스트를 추가했다.
- 플랫폼 회귀 3개 실패 확인 후 수정. 가상 응답 단계 기준 `active query(0) → all query(1) → create(2)`에서 `두 query(0) → create(1)`로 변경. 이는 실제 밀리초나 사이트 로딩 속도 측정이 아니다.
- 같은 URL 일반 클릭 2회: 기존 4 queries + 2 creates → 2 queries + 1 create. Ctrl/Cmd/Shift 및 메뉴의 명시적 새 탭 요청은 별도 의도로 유지한다.
- 현재 창 우선 재사용, 정확한 URL/Notion 경로와 쿼리 보존, API 오류 시 실패 안내와 재시도, 잘못된 URL 거부를 검사했다.
- 드래그 컨트롤러 19개 테스트: 링크·그룹 이동/루트 복귀, 자기 자신·자손·미분류 이동 금지, 깊이 상한, revision·보관함 변경, 외부/위조 payload, 중복 drop, 실패 처리, Escape, 드래그 직후 잘못된 클릭 방지.
- 드래그 payload는 세션 nonce만 포함하며 URL·제목을 외부로 전달하지 않는다. 기존 `moveLink`/`moveGroup`과 저장 충돌 검사·undo를 그대로 사용한다.
- 링크 렌더링은 열린 탭 식별자를 한 번 Set으로 만들고 조회한다. 주소 식별 캐시는 패널 메모리에서 최대 4,096개로 제한하며 저장하거나 전송하지 않는다.
- 독립 코드 검토에서 발견한 두 항목을 수정했다: 명시적 새 탭 요청 차단, 드래그 시작 시 열린 메뉴 닫기 리스너의 이벤트 단계.
