# FAVMOA 0.1.34 · 삭제·초기화 영향 재검토

검증일: 2026-09-25 KST. [개선 큐](USABILITY-IMPROVEMENT-QUEUE.md) 2번 중 링크 제거·그룹 제거·현재 보관함 초기화를 완료했다. 기존 Moa 가져오기·JSON 복원·복원 전 안전 사본 확인창은 후속 범위다.

## 재현과 원인

실제 sidepanel 소스·모델을 합성 DOM/저장소에서 실행했다. 삭제/초기화/이전/복원 6경로 모두 revision 7 확인창에서 revision 8 충돌을 받은 뒤 다시 제출해도 요청은 `[7,7]`이었다. 버튼은 활성이고 설명도 처음 상태에 머물렀다. 링크 제거는 원래 보관함이 삭제되면 재요청이 다른 보관함으로 바뀌었다. 현재 서비스의 revision 차단은 작동하고 있어 실제 잘못된 삭제는 막히지만, 단순 revision 갱신만으로는 안전하지 않았다.

작은 재현 테스트의 RED를 먼저 확인하고 `destructiveDialog`를 통해 고정된 대상·명시적 읽기·새 확인·별도 실행을 연결했다. 백업은 추가 데이터 계약이 필요해 이번 작은 변경에 섞지 않았다.

## 구현 계약

- 원래 보관함과 링크/그룹 ID를 고정한다. 삭제된 대상/보관함은 같은 ID의 다른 보관함 항목이나 기본값으로 대체하지 않는다.
- 충돌하면 실행을 잠그고 **최신 영향 범위 검토**를 제공한다. 이는 `platform.load()`만 호출하며 삭제·초기화·원본 탭/북마크 조회를 실행하지 않는다.
- 링크 제거는 최신 제목·주소·전체 경로, 그룹 제거는 최신 하위 내용과 보존 위치, 보관함 초기화는 최신 그룹/링크 수와 전체 내용을 보여준다. 처음 상태와 최신 상태를 비교할 수 있고 긴 목록은 native details로 펼쳐 본다.
- 모든 충돌 후에는 관련 내용이 같아 보여도 확인 체크 후 별도 실행해야 한다. 재검토/재충돌은 이전 확인을 취소하고 직접 submit으로도 우회되지 않는다.
- 그룹만 제거할 때 링크·하위 그룹은 최신 부모/미분류로 보존한다. 유효한 catalog에 미분류가 없으면 모델이 새로 만들 위치를 설명한다. 미분류 자체 제거는 차단한다. 초기화는 확인한 보관함만 비우고 다른 보관함은 보존한다.
- 원래 보관함이 바뀌어 보이는 백그라운드 탐색이 있어도 고정 대상만 처리하고 성공 시 그 보관함으로 돌아간다. 취소·읽기 실패는 최신 저장 목록과 검색 맥락을 유지한다.
- 잘못되거나 오래된 스냅샷, 취소/대체창 뒤 도착한 응답, 중복 읽기·제출은 실행을 허용하지 않는다. 원래 대상이 없으면 숨겨진 확인칸이 아니라 재검토 버튼에 초점을 둔다. 일반 저장 실패는 기존 확인 상태를 유지해 같은 revision으로 명시적 재시도가 가능하며, 이후 변경은 서비스 충돌 검사로 차단한다.
- 데이터 모델/저장 서비스/권한/고정 확장 ID는 변경하지 않았다. 마지막 내용 편집 1회 Undo와 기존 안전 사본 계약은 그대로다.

## 전달과 한계

사용자 데이터·탭·북마크는 테스트에 사용하거나 변경하지 않았다. 최근 내부 브라우저 연결 실패를 반복하지 않았고 이번 네이티브 화면 검증은 미실행이다. 실제 포인터/키보드/스크린리더와 긴 목록의 시각 배치는 별도 검증이 필요하다.

기존 설치용 `artifacts/favmoa-v0.1.13`이 0.1.33과 일치함을 확인하고 `artifacts/favmoa-before-0.1.34-20260925`에 백업한 뒤 프로그램 파일만 갱신했다. 소스/ZIP 압축 해제본/설치 경로 **39파일 바이트 일치**를 확인했다. Chrome 확장 카드 새로고침은 사용자 확인이 필요하며 이전에 차단된 관리 URL을 다른 경로로 우회하지 않았다. ZIP·백업·합성 원장은 로컬에만 두며 공개 저장소에는 올리지 않는다.

다음은 백업/기존 목록 가져오기 충돌 복구다. 복원점 GET은 boolean만 제공하므로 실제 복원 목록의 읽기 전용 미리보기가 먼저 필요하다. Legacy 원본은 catalog revision과 별개이므로 최신 대상만 검토하고 원본 내용까지 검토했다고 주장하면 안 된다. 자세한 다음 계약은 개선 큐에 남겼다.
