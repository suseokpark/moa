# FAVMOA 0.1.16 · 재귀 그룹

작성일: 2026-09-23 KST · 다음 패치: 0.1.17 · QA: 자동·합성 UI·ZIP 검증 완료, 실설치·파일 업로드 미검증

## 결정과 범위

범용 링크 보관함의 **그룹 → 섹션 → 링크** 고정 구조를 **그룹 안에 하위 그룹과 링크를 함께 담는 구조**로 바꾼다. 화면의 ‘하위 그룹’과 저장 모델은 동일한 `Group`이다. ‘섹션’을 다른 이름으로만 바꾸는 것이 아니라 그룹을 반복해서 중첩할 수 있게 한다.

0.1.15의 밝은 중성색·목록 중심 스타일을 유지한다. Google 연결·Drive 동기화는 계속 보류하고 로컬 저장·JSON 백업을 기본으로 한다. 확장 공개키·ID `ebbgmhdbonpillbfjapebljagnbjembj`·권한 범위·기존 저장 키와 승인된 브랜드 자산은 바꾸지 않는다.

## 화면과 데이터 모델

| 화면 용어 | canonical 모델 | 소속과 내용 |
|---|---|---|
| 보관함 | Library | 최상위 `groups`를 소유하는 컨테이너 |
| 그룹 | Group | 보관함에 직접 속하거나 다른 그룹에 속함 |
| 하위 그룹 | Group | 다른 그룹의 `groups`에 있는 같은 모델. 별도 엔티티 아님 |
| 링크 | Link | 한 그룹의 `links`에 직접 속함 |

canonical catalog는 `schemaVersion: 2`이다. 그룹의 기본 형태는 다음과 같다. 예시는 구조 설명이며 실제 사용자 데이터가 아니다.

```js
{
  id: "group-work",
  name: "업무",
  collapsed: false,
  groups: [
    {
      id: "group-project",
      name: "프로젝트",
      collapsed: false,
      groups: [],
      links: []
    }
  ],
  links: []
}
```

`library.groups` 아래 같은 구조를 재귀적으로 사용한다. 별도 Section 모델이나 `sections` 배열은 새 canonical 데이터에 넣지 않는다. 구형 필드와 메시지는 이전·호환 경계에서만 다룬다. 원본 서비스의 폴더·페이지 하위 탐색은 읽기 전용 원본 정보이며 사용자 그룹과 혼동하지 않는다.

## 사용자 동작과 안전 규칙

1. 보관함에 새 그룹을 만들거나 기존 그룹에 하위 그룹을 만든다. 새 그룹에 자동 미분류 섹션을 붙이지 않는다.
2. 어떤 그룹에도 링크를 직접 저장할 수 있다. 링크 추가·이동에서는 저장할 그룹의 전체 경로를 확인한다.
3. 그룹마다 접힘 상태를 독립적으로 저장한다. 현재 링크 찾기는 필요한 조상 경로를 펼쳐 위치를 표시한다.
4. 그룹을 이동하면 자식 그룹·링크를 포함한 하위 트리 전체가 따라간다. 자기 자신 또는 모든 자손은 이동 목적지가 될 수 없다.
5. 최상위 시스템 미분류 그룹은 이름 변경·삭제·이동할 수 없다. 직접 링크와 사용자 하위 그룹은 추가할 수 있다.
6. 사용자 그룹 삭제는 내용 삭제가 아니다. 직접 링크와 자식 그룹을 부모로 올린다. 최상위 사용자 그룹을 삭제할 때 내용은 미분류 그룹으로 옮긴다. 원본 웹 문서나 브라우저 북마크는 바꾸지 않는다.
7. 그룹 깊이는 최상위 그룹부터 **32단계**까지다. 무한 재귀·과도한 입력을 막는 구조 안전 상한이며, 32단계로 정리하도록 권장하는 UI 목표가 아니다. 이동 후 생기는 전체 깊이도 검사한다.
8. 중복 ID·중복 목적지·잘못된 URL·크기 상한·오래된 revision 검증은 계속 적용한다. 실패를 빈 목록으로 처리하거나 사용자 데이터를 초기화하지 않는다.

## schema 1 → 2 변환

| schema 1 입력 | schema 2 출력 |
|---|---|
| 기존 그룹 | 기존 위치의 Group. 직접 링크와 자식 그룹을 담을 수 있음 |
| 사용자가 만든 섹션 | 기존 그룹 아래 하위 Group. 이름·내용·접힘·분류 순서를 유지 |
| 시스템 ID로 식별되는 자동 미분류 섹션 | 별도 그룹을 만들지 않고 해당 링크를 부모 Group의 직접 링크로 이동 |
| 이름만 ‘미분류 섹션’인 사용자 섹션 | 일반 사용자 하위 Group으로 유지. 이름만 보고 합치지 않음 |
| 구형 undo·JSON 복원 안전 사본 | 사용할 때 schema 2로 정규화 |

그룹으로 변환되는 ID는 유효성·전역 중복·예약 ID 충돌을 고려해 결정적으로 매핑한다. 입력이 같으면 반복해서 읽어도 같은 결과여야 한다. 링크 제목·URL·아이콘·동일성은 보존하고, 확인되지 않은 원본 제목을 새로 추정하지 않는다.

### 저장 경계

- GET은 schema 2 모델을 반환하더라도 원래 저장 값을 쓰거나 지우지 않는다.
- schema 1 데이터에서 **처음 실제 변경을 성공적으로 저장할 때**, 기존 catalog·일반 undo·복원 안전 사본의 저장 값을 `favmoa:schema-v1-backup:v1`에 한 번 보존하고 새 catalog 저장과 함께 적용한다.
- 이 사본이 이미 있으면 다음 편집으로 덮어쓰지 않는다. 일반 편집의 되돌리기와 JSON 복원 전 안전 사본은 별개로 계속 동작한다.
- no-op은 쓰기나 이전 완료로 취급하지 않는다. 검증 실패·revision 충돌·저장 공간 부족 등으로 저장하지 못하면 기존 데이터와 복구 값을 유지한다.
- 기존 저장 키의 이름은 그대로다. 키 이름에 들어 있는 버전 문자열과 catalog 내부 `schemaVersion`은 같은 의미가 아니다.
- 내부 이전 사본은 자동 앱 다운그레이드 기능이나 외부 파일 백업을 대신하지 않는다.

### 저장 공간

현재 catalog, 일반 undo와 JSON 복원 전 사본으로 최대 3개 catalog가 쓰일 수 있다. **이전 원형 사본에는 추가로 최대 3개 catalog 값이 남을 수 있으므로 저장소 전체가 3개 catalog에 그치지 않는다.** 구형 Notion 원본·캐시·이전 스냅샷도 저장 공간을 함께 쓴다.

개별 catalog 형식상 상한은 간결한 UTF-8 JSON **5MiB**, 가져올 JSON 파일은 포장 정보를 포함해 **6MiB**, 전체 링크는 **10,000개**, 보관함·그룹·링크 합산 항목은 **20,000개**다. 형식상 상한이 Chrome 저장 공간의 확보를 보장하지는 않는다. 첫 schema 2 저장에는 이전 원형을 함께 보관할 여유도 필요하다. 공간 부족 시 이전 원본이나 다른 사용자 데이터를 자동 삭제하지 않고 오류를 알린다.

## JSON 백업과 버전 호환성

- 0.1.16은 기존 schema 1 JSON을 읽고 schema 2로 변환해서 가져온다.
- 새 JSON 내보내기는 schema 2 그룹 구조를 보존한다. 새 버전에 다시 가져와도 중첩 그룹·직접 링크를 유지해야 한다.
- **0.1.15 이하에서는 schema 2 백업을 읽을 수 없다.** 이를 양방향 호환이나 자동 다운그레이드 지원으로 설명하지 않는다.
- 업데이트 전에 구형 버전에서 schema 1 JSON 파일을 별도로 저장한다. 구형 버전으로 돌아갈 가능성이 있으면 이 파일을 유지한다. 이후 새 버전에서 편집한 내용은 업데이트 전 파일에 포함되지 않는다.
- 새 저장소 위에 구형 코드를 덮어쓰는 다운그레이드는 지원하지 않는다. 내부 이전 사본을 근거로 사용자가 안전하게 구형 버전으로 돌아갈 수 있다고 보장하지 않는다.
- JSON 불러오기는 변환 전후 모두 **전체 보관함 교체**다. 현재 목록과 자동 병합하지 않는다. 실제 교체 전 안전 사본과 취소·비교·사전 내보내기 경로를 유지한다.

## 기존 Notion 호환 화면

Notion 수신함 옆 내부 화면은 기존 **그룹 → 섹션 → Favorite** 구조를 계속 사용한다. 이 호환 화면과 범용 링크 보관함은 서로 다른 모델이며, `nfs:workspace:`와 `nfs:metadata:` 원본 키를 재귀 그룹 업데이트 때문에 바꾸거나 지우지 않는다.

사용자가 **기존 Moa 가져오기**를 실행할 때만 저장된 Notion 트리의 복사본을 schema 2로 변환한다. 이후 각 화면의 편집은 양방향으로 동기화하지 않는다. 구형 데이터의 제목 복구는 기존 원본 관찰 범위·캐시 규칙을 따른다.

## 검증 결과와 남은 범위

새 전체 Node 검사 **367/367**과 localhost의 합성 데이터 UI 검증을 실행했다. 상세 재현·스크린샷·패키지 수치는 [0.1.16 QA](QA-0.1.16.md)에 기록한다. 아래의 ‘Node’는 자동 모델/계약 검사이고, ‘합성 UI’는 실제 설치 확장 데이터나 실계정 검증을 뜻하지 않는다. 과거 버전의 테스트 수를 재사용하지 않았다.

| 영역 | 확인할 동작 | 상태 |
|---|---|---|
| 재귀 모델 | 직접 링크+여러 깊이 자식, 독립 접힘, 빈 그룹, 중복 ID·잘못된 입력 | Node 통과, 혼합 트리 합성 UI 확인 |
| 그룹 이동 | 루트/하위 간 전체 이동, 자기·자손 목적지 거부, 깊이 32 경계 | Node 통과, 하위 트리 전체 이동·되돌리기 합성 UI 확인 |
| 그룹 삭제·보호 | 부모/미분류로 내용 보존, 시스템 그룹 rename/delete/move 거부 | Node 통과 |
| schema 이전 | 사용자/자동 섹션, 같은 이름의 사용자 섹션, 결정적 변환, 링크·접힘 유지 | Node 통과, 기존 합성 v1의 링크 3개 이름 유지 확인 |

실제 설치 데이터·실계정·브라우저 권한과 파일 선택 업로드는 도구 접근 제한으로 검증하지 않았다. 구형 Notion suite의 짧은 메뉴 마지막 동작 도달 검사에서 한 번 실패했으나 별도 사용성 검사 19/19와 전체 재실행 8/8은 통과했다. 타이밍·메뉴 위치 재계산 가능성이 있으나 원인은 미확정이고, 구형 런타임을 이번 작업에서 변경하거나 이 실패를 고쳤다고 주장하지 않는다. Google 연결과 실제 Drive 동기화는 계속 보류다.
